# FLUX Source-Code Guide

This guide explains how the source fits together and where to make changes safely.

## 1. Web application

### `artifacts/flux-file-intelligence/src/main.tsx`

Browser entry point. It mounts the React application and the shared providers used by the product.

### `artifacts/flux-file-intelligence/src/App.tsx`

This is the main product surface. It currently contains:

- `toolCatalog`: the canonical list of tool slugs, titles, categories, icons, descriptions, and visual accents.
- `Logo`, `AppHeader`, and `AppShell`: public and workspace navigation.
- `UploadPanel`: file selection, drag-and-drop, browser-to-base64 conversion, file registration, and job creation.
- `ToolPage`: reusable upload/job-monitor/download experience for every catalog tool.
- `CatalogToolRoute`: resolves `/:slug` against `toolCatalog`.
- `Dashboard`: dashboard metrics, files, recent activity, and quick tools.
- `DocumentChat`: selected-document question surface.
- `Pricing`, `AccountPage`, `AuthPage`, and trust pages.
- `Router`: Wouter route table.

When adding a new tool:

1. Add one catalog entry with a stable slug.
2. Make the slug match a backend operation branch.
3. Keep the page on the shared `ToolPage` unless the tool needs a custom input form.
4. Add an operation-specific input contract if the tool needs more than a file.
5. Add an end-to-end test using a small fixture file.

### `artifacts/flux-file-intelligence/src/index.css`

Global FLUX visual system: palette, typography, textures, spacing helpers, and motion. Keep product-level style changes here instead of scattering global CSS through components.

### `artifacts/flux-file-intelligence/src/components/ui/`

Reusable Radix/Tailwind UI primitives. Use these when a new surface needs a dialog, form control, toast, table, or accessible interaction instead of inventing a one-off primitive.

## 2. API server

### `artifacts/api-server/src/app.ts`

Creates the Express application, installs logging, CORS, JSON/body parsing, and mounts all routes under `/api`.

The JSON body limit is intentionally finite because the current upload flow sends file bytes in JSON. The browser rejects files larger than 24 MB before upload.

### `artifacts/api-server/src/index.ts`

Reads the workflow-provided `PORT` and starts the Express server. Do not hardcode the port in application code.

### `artifacts/api-server/src/routes/files.ts`

Owns file records and the current in-process byte store:

- `files`: file metadata records.
- `fileContents`: uploaded bytes and MIME metadata keyed by file ID.
- `POST /files`: validates the generated `CreateFileBody`, creates the record, and stores the bytes.
- `GET /files`: lists workspace files.
- `GET /files/:id`: returns one metadata record.

The `StoredFile` type is deliberately separate from the public `FileRecord` response so raw file bytes are never serialized into list/detail responses.

### `artifacts/api-server/src/routes/processing.ts`

Owns processing jobs and result bytes:

- `POST /processing/jobs`: validates the file and operation, accepts an optional question for document chat, creates a queued job, and starts `executeJob`.
- `executeJob`: loads the uploaded bytes, updates progress, calls `processFile`, stores the output, and updates the result metadata.
- `GET /processing/jobs/:id`: returns job state for polling.
- `GET /processing/jobs/:id/result`: streams the generated bytes with download headers.

This is intentionally a job-shaped API even though the current worker runs inside the API process. A durable queue can replace `void executeJob(job)` later without changing the frontend contract.

### `artifacts/api-server/src/lib/processor.ts`

The operation engine. It is a dispatcher keyed by the catalog slug and returns a common:

```ts
type ProcessorResult = {
  bytes: Buffer;
  name: string;
  contentType: string;
};
```

Important helpers:

- `extractText`: PDF, DOCX, XLSX, and plain-text extraction.
- `createTextPdf`: creates a real PDF from text.
- `imageToPdf`: embeds PNG/JPEG bytes into a PDF.
- `convertImage`: delegates image conversion/compression to ImageMagick.
- `pdfOperation`: handles PDF rendering, page operations, compression, signing, and redaction.
- `makePresentation`: generates a real PPTX using PptxGenJS.
- `runDeveloperTool`: handles JSON, CSV, JWT, Base64, UUID, regex, timestamps, SQL, and minification.
- `generateWithOpenAI`: optionally calls OpenAI from the server for source-grounded document-intelligence artifacts. It reads `OPENAI_API_KEY` only from server environment secrets and returns `null` on provider failure so the local fallback can run.
- `processFile`: maps all catalog operations to handlers.

The engine uses temporary files only for external command-line tools and removes them in `finally` blocks.

## 3. API contract and generated code

### `lib/api-spec/openapi.yaml`

Source of truth for REST paths, request bodies, response bodies, enums, and optional result metadata.

### `lib/api-client-react/`

Orval-generated React Query hooks and TypeScript models used by the web app. Examples include:

- `useCreateFile`
- `useCreateProcessingJob`
- `useGetProcessingJob`
- `useListFiles`
- `useGetDashboardSummary`

### `lib/api-zod/`

Orval-generated Zod validators used by the API server. The server parses incoming bodies and response objects through these schemas.

After changing the OpenAPI file:

```bash
pnpm --filter @workspace/api-spec run codegen
```

Do not manually edit generated output.

## 4. Billing source

### `artifacts/api-server/src/lib/whopClient.ts`

Server-only Whop client initialization through the connected Replit integration. It does not expose credentials to the browser.

### `artifacts/api-server/src/routes/billing.ts`

Billing endpoints:

- `/whop/config`: exposes safe public plan metadata.
- `/whop/checkout`: returns the hosted Whop checkout URL.
- `/whop/access`: verifies a Whop user token and checks product access server-side.

### `Pricing` and `AccountPage` in `App.tsx`

The frontend starts hosted checkout and displays verified/free account state. It does not decide whether a user has paid.

## 6. Safe extension pattern

For a new backend-backed operation:

1. Add or update the OpenAPI request/response shape.
2. Run API codegen.
3. Add the operation to `toolCatalog`.
4. Implement the operation in `processFile`.
5. Return a meaningful filename and content type.
6. Verify the job reaches `completed` and the result downloads.
7. Test invalid input and tool-specific failures.
8. Restart the API and web workflows.

For a tool requiring user options, extend `ProcessingInput` with an optional validated `options` object rather than encoding options into the operation slug.

## 7. Known boundaries

- In-process maps are not durable storage.
- Authentication screens are currently product placeholders.
- Whop access verification needs a real FLUX-to-Whop identity bridge for external web sessions.
- Document-intelligence handlers use OpenAI when `OPENAI_API_KEY` is configured and fall back to deterministic local processing when it is unavailable.
- Multi-file operations such as true PDF merging need a multipart or file-selection input contract; the current shared page sends one source file per job.
